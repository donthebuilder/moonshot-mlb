THREADS — WHAT YOU DO, AND WHAT'S ALREADY DONE
2026-09-20

The code is in and inert. It posts nothing until two env vars exist AND a
third is flipped on, so this can sit in production safely while you do the
Meta side.

=============================================================
THE GOOD NEWS: YOU DO NOT NEED APP REVIEW
=============================================================

Meta App Review (weeks, screencasts, business verification) is required to
publish to OTHER people's accounts. You are publishing to YOUR OWN — the
CALLED IT profile — which you can do straight away by adding that account as
a tester on your own Meta app.

That is the whole difference between "three to six weeks" and "this evening."

=============================================================
WHAT YOU DO — ABOUT 30 MINUTES
=============================================================

1. developers.facebook.com → My Apps → Create App → use case "Access the
   Threads API".

2. In the app, add the Threads API product. Request these two scopes:

       threads_basic
       threads_content_publish

3. App roles → add the CALLED IT Threads account as a TESTER, then accept the
   invite from that account's Threads settings.

4. Generate a user access token for that account through the Threads OAuth
   flow, then exchange it for a LONG-LIVED token (60 days) at the
   /access_token endpoint.

   ⚠️ 60 DAYS. It can be refreshed any time inside that window. Put a
   reminder in your calendar for day 50 — an expired token means the mirror
   goes quiet, and quiet is the failure mode you and I have now been bitten
   by twice.

5. Get the numeric Threads user id (GET /me with the token — the check route
   below prints it for you).

6. Vercel → project → Settings → Environment Variables:

       THREADS_USER_ID        = the numeric id
       THREADS_ACCESS_TOKEN   = the long-lived token
       THREADS_MIRROR         = leave UNSET for now

7. Redeploy, then hit:

       /api/dash/threads/check

   Read-only. It tells you whether the vars are set, and which profile the
   token actually belongs to. Check the username is CALLED IT and not your
   personal account BEFORE step 8.

8. One real test post:

       /api/dash/threads/check?go=1&key=<CALLEDIT_SECRET>

   Look at it on Threads.

9. Only then set THREADS_MIRROR=1 and redeploy. From that moment every post
   the account sends to X also goes to Threads.

=============================================================
THE FUNNEL — THE ACTUAL REASON TO DO THIS
=============================================================

On X a post is $0.015 and a post CONTAINING A URL is $0.200. Thirteen times.
That is why the link has been in zero tweets since 09-05, and why "turn the
link on" has sat at the top of every priority list I've handed you and never
got done — it was never laziness, it was $24/month for something you weren't
sure would convert.

That constraint does not exist on Threads. Posting is free, so the link is
free.

THE LINK GOES IN A REPLY, NOT THE POST. Default mode. The post goes up clean
and the link follows underneath, one tap away. Two reasons pointing the same
way: every feed ranks a link-out post below one that keeps people in the app,
so a URL in the body costs the post the reach that made it worth linking
from — and a post ending in a URL reads like an ad, while a post that says
something true and then offers the receipt reads like a sports account. The
free 1,000 replies/day are what make this affordable here and what made it
unaffordable on X.

  THREADS_LINK_MODE = reply   (default — link as the first reply)
                      inline  (link in the body)
                      off

NOT EVERY POST. A link under all forty of a night's homer alerts is a spam
pattern and trains people to scroll past. Thirteen ANCHOR kinds carry one:

  MLB   pregame · board · board_results · accountability · recap · weekly
        monthly · callofnight · community_pick · thefour
  NFL   nfl_board · nfl_results · nfl_spotlight · nfl_bigweek

Everything else posts clean — the live alerts above all. They are the reach;
the anchors are what converts it.

WHERE IT SENDS. MLB posts land on /called — the public proof page, no account
needed. That is the right first door for a stranger: it answers the question
the post just raised instead of asking them to sign up before they believe
anything. Football has no public equivalent yet, so NFL posts land on the
front page with the live NFL tiles. Building /called's football twin is
probably the highest-value thing on the list after this.

EVERY LINK IS TAGGED. ?utm_source=threads&utm_medium=social&utm_campaign=<kind>
so you can see which post type actually sends people, not just that Threads
does. Nothing identifying is in the query string.

SEE IT BEFORE IT'S LIVE — needs no token, posts nothing:

    /api/dash/threads/check?preview=1

That prints all thirteen link lines exactly as they'll appear. Read the copy
and tell me what to change; it's the only part of this a stranger sees.

=============================================================
FOUR THINGS THREADS WON'T DO, AND WHAT I DID ABOUT EACH
=============================================================

1. NO NATIVE POLL. THE BOT VS THE PEOPLE is X-only. Mirrored as text it would
   ask a question nobody can answer, so a post carrying a poll is SKIPPED
   rather than degraded.

2. NO IMAGE BYTES. (You said text-only is fine — noted, not built.) X takes the card's PNG directly. Threads only takes a
   PUBLIC image_url it fetches itself. The cards are rendered in memory and
   handed straight to X, so mirrored posts are TEXT-ONLY right now.

   This is the one real gap. /api/dash/homers/card can already serve a public
   URL for three kinds (homer, recap, pregame); the other ~20 post types have
   no public card URL. Making the cards cross is a separate job — say the word
   and I'll scope it.

3. REPLIES NEED THEIR PARENT. A reply on Threads must point at the Threads id
   of the post it answers. When the parent was posted in the same tick, that
   pairing is in memory and the reply threads correctly. When it wasn't — the
   homer board-reply pass reads x_post_id back out of the database, often
   minutes later on a fresh instance — the mirror SKIPS it rather than posting
   an orphan that reads as a non sequitur.

   The proper fix is a threads_post_id column next to x_post_id in homer_feed
   and nfl_td_feed, same as the reply_post_id column we added last night. Not
   built yet: no point storing ids until a token exists.

4. 500 CHARACTERS, not 280. Longer than everything we write, so nothing needs
   rewriting. The refit only ever touches a Premium long post.
